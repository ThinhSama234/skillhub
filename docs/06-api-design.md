# skillhub API Design

## 0. Identifier Type Constraints

- All user identifiers appearing in APIs must be `string`.
- This constraint applies to path parameters, query parameters, request body fields, response DTO fields, and business data content within the unified response structure.
- Any integer user identifier patterns from older drafts are now invalid; the formal frontend-backend contract only allows string user identifiers.

## 1. Response Structure Specification

Except for binary stream endpoints such as file downloads and file content reads, all JSON APIs must use the following unified success response structure:

```json
{
  "code": 0,
  "msg": "Success",
  "data": {},
  "timestamp": "2026-03-12T06:00:00Z",
  "requestId": "req-123"
}
```

Constraints:

- `code`: Fixed to `0` on success; on failure, fixed to the HTTP status code, e.g. `400`, `401`, `403`, `500`.
- `msg`: A user-readable message returned to the caller. Must be generated via Spring Boot `MessageSource` + i18n mechanism; hard-coding in controllers is prohibited.
- The locale for `msg` must be automatically retrieved from the request context via `LocaleContextHolder` at the response wrapping layer or global exception handling layer; explicitly passing `Locale` in controllers/services is prohibited.
- `data` carries the actual business data; lists, pagination objects, detail objects, and operation result objects must all be placed under `data`.
- Paginated responses must use `{ items, total, page, size }`; directly exposing Spring `Page` internals such as `content/pageable/sort/first/last` is prohibited.
- `timestamp`: Response creation timestamp, automatically generated by the backend.
- `requestId`: Request trace ID, uniformly injected by the backend to facilitate log tracing.
- The controller layer must not directly return `Map`, bare DTOs, bare `Page`, or bare `List` as JSON success responses.
- Regular JSON endpoints should return the unified response DTO directly; only binary endpoints (file downloads, file previews, etc.) requiring custom status codes or headers should retain `ResponseEntity`.
- Operations such as delete, withdraw, and move tag must also return the unified JSON structure; if there is no entity data, return `data.message` or `data=null`, but the outer structure must not change.
- Error responses and success responses share the same outer structure; a separate exception JSON structure is no longer used.
- `msg` in error paths must also be generated via Spring Boot standard i18n; parameter validation exceptions, domain exceptions, and authentication/authorization exceptions must all go through the unified `@RestControllerAdvice` exit point.
- Binary stream endpoints retain raw HTTP semantics without the `code/data` wrapper:
  - `/download`
  - `/file`
  - Other endpoints returning `application/octet-stream`, `application/zip`, etc.

Success response example:

```json
{
  "code": 0,
  "msg": "Published successfully",
  "data": {
    "skillId": 123,
    "version": "1.0.0"
  },
  "timestamp": "2026-03-12T06:00:00Z",
  "requestId": "req-123"
}
```

Error response example:

```json
{
  "code": 403,
  "msg": "Namespace admin or owner permission required",
  "data": null,
  "timestamp": "2026-03-12T06:00:00Z",
  "requestId": "req-123"
}
```

## 7.1 Public API (Anonymous Access)

| Method | Path | Description |
|--------|------|-------------|
| GET | `/api/v1/skills` | Search/list (anonymous returns only PUBLIC skills) |
| GET | `/api/v1/skills/{namespace}/{slug}` | Skill detail (PUBLIC accessible anonymously) |
| GET | `/api/v1/skills/{namespace}/{slug}/versions` | Version list |
| GET | `/api/v1/skills/{namespace}/{slug}/versions/{version}` | Version detail |
| GET | `/api/v1/skills/{namespace}/{slug}/versions/{version}/files` | File manifest |
| GET | `/api/v1/skills/{namespace}/{slug}/versions/{version}/file?path=...` | Read a single file (query param to avoid path `/` parsing issues) |
| GET | `/api/v1/skills/{namespace}/{slug}/download` | Download the default installation version (latest published version) |
| GET | `/api/v1/skills/{namespace}/{slug}/versions/{version}/download` | Download a specific version package |
| GET | `/api/v1/skills/{namespace}/{slug}/resolve` | Resolve skill version (supports query params: `version`, `tag`, `hash`) |
| GET | `/api/v1/skills/{namespace}/{slug}/tags/{tagName}/download` | Download by tag (resolves the version the tag points to, then downloads) |
| GET | `/api/v1/skills/{namespace}/{slug}/tags/{tagName}/files` | View file manifest by tag |
| GET | `/api/v1/skills/{namespace}/{slug}/tags/{tagName}/file?path=...` | Read a single file by tag |
| GET | `/api/v1/namespaces` | Public namespace list |
| GET | `/api/v1/namespaces/{slug}` | Namespace detail |

Public API visibility rules:
- `PUBLIC` skills: accessible to logged-in users if a published version exists; anonymous access is still subject to namespace type restrictions on download/resolve endpoints
- `NAMESPACE_ONLY` skills: accessible only to namespace members (login required)
- `PRIVATE` skills: accessible only to the owner and namespace ADMINs and above (login required)
- If `latest_version_id = null`, the skill is not publicly visible even if `visibility=PUBLIC`; only the owner can access it
- When `hidden=true`, ordinary visitors cannot access it; only the owner or the namespace `ADMIN` / `OWNER` can access it

The `data` field of `GET /api/v1/skills/{namespace}/{slug}/versions/{version}` must include, in addition to basic version information:

- `parsedMetadataJson`: The full JSON-serialized result of the `SKILL.md` frontmatter
- `manifestJson`: A JSON summary of the version file manifest

| POST | `/api/v1/auth/direct/login` | Explicit compatibility login entry for direct-connect auth provider (disabled by default) |
| POST | `/api/v1/auth/session/bootstrap` | Explicitly attempt to exchange an external passive session for a skillhub Session (disabled by default) |

`/api/v1/auth/providers` response example:

```json
{
  "code": 0,
  "msg": "Retrieved successfully",
  "data": [
    { "id": "github", "name": "GitHub", "authorizationUrl": "/oauth2/authorization/github" }
  ],
  "timestamp": "2026-03-12T06:00:00Z",
  "requestId": "req-123"
}
```

The frontend dynamically renders login buttons based on this endpoint; adding a new provider does not require frontend code changes.

`/api/v1/auth/methods` returns the unified login method directory. Typical entries include:

- `PASSWORD`: Existing local username/password login
- `OAUTH_REDIRECT`: OAuth redirect login
- `DIRECT_PASSWORD`: Disabled-by-default direct-connect auth compatibility entry
- `SESSION_BOOTSTRAP`: Disabled-by-default passive session bootstrap entry

Example:

```json
{
  "code": 0,
  "msg": "Retrieved successfully",
  "data": [
    {
      "id": "local-password",
      "methodType": "PASSWORD",
      "provider": "local",
      "displayName": "Local Account",
      "actionUrl": "/api/v1/auth/local/login"
    },
    {
      "id": "oauth-github",
      "methodType": "OAUTH_REDIRECT",
      "provider": "github",
      "displayName": "GitHub",
      "actionUrl": "/oauth2/authorization/github"
    }
  ],
  "timestamp": "2026-03-12T06:00:00Z",
  "requestId": "req-123"
}
```

`/api/v1/auth/session/bootstrap` request example:

```json
{
  "provider": "private-sso"
}
```

`/api/v1/auth/session/bootstrap` protocol constraints:

- Disabled by default in the open-source edition; must explicitly enable `skillhub.auth.session-bootstrap.enabled=true`
- Returns `403` when disabled
- Returns `400` when the provider does not exist
- Returns `401` when the external session does not exist or validation fails
- On success, returns the same user structure as `/api/v1/auth/me` and establishes a standard Session

`/api/v1/auth/direct/login` request example:

```json
{
  "provider": "private-sso",
  "username": "alice",
  "password": "secret"
}
```

`/api/v1/auth/direct/login` protocol constraints:

- Disabled by default in the open-source edition; must explicitly enable `skillhub.auth.direct.enabled=true`
- Returns `403` when disabled
- Returns `400` when the provider does not exist
- On success, returns the same user structure as `/api/v1/auth/me` and establishes a standard Session
- `/api/v1/auth/local/login` is retained as the existing local account entry point

### Skill Lifecycle Management

| Method | Path | Description |
|--------|------|-------------|
| POST | `/api/v1/skills/{namespace}/{slug}/archive` | Archive a skill (namespace ADMIN or owner) |
| POST | `/api/v1/skills/{namespace}/{slug}/unarchive` | Restore from archive (namespace ADMIN or owner) |
| DELETE | `/api/v1/skills/{namespace}/{slug}/versions/{version}` | Delete a DRAFT/REJECTED version |
| POST | `/api/v1/skills/{namespace}/{slug}/versions/{version}/rerelease` | Re-release a new version from an existing published version (namespace ADMIN or owner) |

The skill lifecycle read model in the current codebase no longer relies on assembled fields like `latestVersionStatus` / `viewingVersionStatus`; instead, it uniformly uses the following projections:

- `headlineVersion`: The primary version to display on the current page
- `publishedVersion`: The current latest distributable published version
- `ownerPreviewVersion`: A `PENDING_REVIEW` preview version visible to the owner / namespace administrator
- `resolutionMode`: `PUBLISHED` / `OWNER_PREVIEW` / `NONE`

Where:

- Public detail, public installation, and public search all use only `publishedVersion`
- The owner detail page may fall back to `headlineVersion` pointing to `ownerPreviewVersion` only when there is no published version to display
- Promotion to global always uses `publishedVersion.id`
- `hidden` is an independent governance override layer, not part of the lifecycle state machine
- Regular version detail endpoints only expose `PUBLISHED` versions and an owner's preview of their own `PENDING_REVIEW` version; `DRAFT / REJECTED / YANKED` are not exposed through this endpoint

The `data` in a successful publish response must include at minimum:

- `skillId`
- `namespace`
- `slug`
- `version`
- `status`
- `fileCount`
- `totalSize`

Publish status constraints:

- After a regular user successfully publishes, `status` is `PENDING_REVIEW`
- When a user with `SUPER_ADMIN` publishes via Web, `/api/v1/publish`, or `/api/v1/publish`, `status` is `PUBLISHED`, and they are not required to be a member of the target namespace
- The current version maintains this review policy; a "publish directly for everyone" mode is no longer provided
- Withdrawing from review does not delete the version record; instead it transitions `PENDING_REVIEW → DRAFT`

### ClawHub CLI Protocol Compatibility Layer

Phase 1 not only provides skillhub's own CLI API but must also expose a set of registry APIs compatible with the ClawHub CLI.

- Goal: Allow existing ClawHub CLI to connect directly to skillhub by configuring a registry base URL
- Scope: Phase 1 focuses on covering the core endpoints the ClawHub CLI depends on: search, version resolution, download, publish, whoami
- Requirement: The compatibility layer should primarily maintain the existing ClawHub CLI request/response semantics; if the internal domain model differs, use an adapter layer for protocol translation rather than requiring clients to adapt to skillhub's private protocol
- Requirement: The compatibility layer is included in OpenAPI or a separate compatibility protocol document, maintained as a formal external contract
- Requirement: The compatibility layer coexists with skillhub's own `/api/v1/**`; both share the same set of permissions, auditing, rate limiting, and domain services
- Non-goal: Frontend pages do not directly depend on the compatibility layer; it serves existing ClawHub CLI and related automation scripts

The minimum capability categories the compatibility layer must cover:

- Registry metadata: skill search, skill detail, version list, tag/default version resolution
- Artifact resolution: resolve download URL/download stream by skill coordinates or version
- Publish workflow: package upload and publish result return
- Integrity check: version existence check, digest/hash comparison, whoami/token context confirmation

If the existing ClawHub CLI protocol differs from skillhub's own endpoints, documentation follows the "ClawHub CLI protocol compatibility" standard; skillhub internal APIs may continue to maintain their current style.

## 7.8 `latest` Semantics

`latest` automatically follows the most recently published version and cannot be manually moved.

- `skill.latest_version_id`: Automatically updated each time a review is approved; always points to the most recent PUBLISHED version
- When the current latest published version is yanked, `latest_version_id` must be recalculated to point to the next most recent `PUBLISHED` version; if none exists, `null` is allowed
- `latest` tag: System-reserved, read-only, automatically synchronized with `latest_version_id`
- Custom tags (e.g., `beta`, `stable-2026q1`): Can be manually created and moved to pin installation channels

| Scenario | Field Used | Description |
|----------|-----------|-------------|
| Search index content | `publishedVersion` / `latest_version_id` | External protocol still calls it latest, but internal semantics must be equivalent to the most recently published version |
| `/download` (without version number) | `publishedVersion` / `latest_version_id` | Download the most recently published version |
| CLI `install @team/skill` | `publishedVersion` / `latest_version_id` | Equivalent to `@latest` |
| CLI `install @team/skill@beta` | `skill_tag` query | Version pointed to by a custom tag |

## 7.9 Resolve Endpoint Description

`GET /api/v1/skills/{namespace}/{slug}/resolve` is used to resolve skill versions and supports the following query params:

| Parameter | Type | Description |
|-----------|------|-------------|
| `version` | string | Exact version number (e.g., `1.2.0`) |
| `tag` | string | Tag name (e.g., `beta`, `latest`) |
| `hash` | string | Fingerprint hash, used to determine if the local version is in sync with the registry |

Resolution priority:
1. `version` and `tag` cannot both be passed at the same time; passing both returns `400 Bad Request`
2. Only `version`: exact match on version number
3. Only `tag`: query the `skill_tag` table to get `target_version_id`
4. Only `hash`: iterate over published versions and compare fingerprints
5. None passed: return the most recently published version; in implementation, can be resolved via `latest_version_id` or an equivalent published projection

Response:

```json
{
  "code": 0,
  "msg": "Retrieved successfully",
  "data": {
    "skillId": 456,
    "namespace": "team-name",
    "slug": "my-skill",
    "version": "1.2.0",
    "versionId": 123,
    "fingerprint": "sha256:abc123...",
    "downloadUrl": "/api/v1/skills/team-name/my-skill/versions/1.2.0/download"
  },
  "timestamp": "2026-03-12T06:00:00Z",
  "requestId": "req-123"
}
```

When `hash` matches, additionally returns `"matched": true`; when it does not match, returns the latest version info + `"matched": false`.

## 7.10 ClawHub CLI Compatibility Layer API

Authentication: `Authorization: Bearer <token>`. Bearer Tokens may come from CLI Device Flow or platform API Tokens.

### Compatibility Layer Adaptation Notes

- The compatibility layer is an independent controller layer that internally calls the same domain services as the native API
- On request entry, canonical slugs are converted to `(namespace_id, skill_slug)` coordinates
- On response return, internal coordinates are converted to canonical slugs
- The compatibility layer does not expose the namespace concept; it is transparent to the ClawHub CLI
- During publish, if the canonical slug contains `--`, it is parsed as a team namespace publish; otherwise it publishes to the global namespace
- The compatibility layer's authentication reuses the skillhub Bearer Token system; ClawHub CLI can use it after logging in or configuring a token

## 7.11 Rate Limiting

Implemented in two phases:

### Phase 1: Basic Rate Limiting at the Ingress Layer

Use Nginx Ingress `limit-req` to apply global per-IP rate limiting, covering authentication, search, download, and other anonymously accessible endpoints to prevent basic abuse and crawling.

### Phase 2: Fine-grained Rate Limiting at the Application Layer

Redis sliding window-based, fine-grained per-user/endpoint rate limiting.

| Endpoint Category | Rate Limit Policy |
|-------------------|-------------------|
| Search API | 60 requests/minute for logged-in users; 20 requests/minute anonymous (by IP) |
| Download API | 120 requests/minute for logged-in users; 30 requests/minute anonymous (by IP) |
| Publish API | 10 requests/hour (per user) |
| Auth API | 30 requests/minute (by IP) |

When rate limit is triggered, returns `429 Too Many Requests` + `Retry-After` header.

## 7.12 API Design Principles

### Native API (`/api/v1/*`)

- Unified response wrapper: `{ code, message, data, timestamp }`
- Pagination format: `{ items, total, page, size }`
- Error code system: business error codes + HTTP status codes in combination
- Versioning strategy: URL path versioning `/api/v1/`
- Idempotency: write operations deduplicated via `X-Request-Id` + Redis (TTL 24h)

### Compatibility API (`/api/v1/*`)

- Response format strictly follows the ClawHub protocol without the unified response wrapper
- Error responses follow the ClawHub format: `{ error: string, message: string }`
- Pagination format follows the ClawHub format: `{ results, total, page, limit }`

### OpenAPI Documentation Separation

Two separate OpenAPI specs are generated:
- `openapi-native.json`: skillhub Native API, used for frontend SDK generation
- `openapi-compat-clawhub.json`: ClawHub compatibility layer API, used for compatibility testing and documentation
